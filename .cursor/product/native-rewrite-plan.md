# Repdraft: rewrite (native-first)

**Статус:** глобальный rewrite. Источник правды по направлению продукта - этот файл + [`mvp.mdc`](../rules/mvp.mdc) + [`delivery.md`](./delivery.md). Старые MVP-спеки и research-доки сняты.

**North star:** улучшить UX священного цикла, не feature count. Метрика: phone → completed set. Быстро на слабых телефонах.

| Фаза | Статус | Суть |
|---|---|---|
| A Метрики цикла | в коде | `domain/loopMetrics.ts`, снимок в профиле (tester) |
| B Opt-in Quest | **снят с продукта** | UI Quest/ачивок удалён (web + RN). Domain (`quest.ts`, `achievements.ts`) не удалён: им пользуется progress (`weekKeyFromDate`). Курс — профессиональный логгер, без RPG. |
| C Часы | spike ADR | [`.cursor/product/watch-session-ownership.md`](./watch-session-ownership.md); native UI отдельно |
| D RN ядро | почти паритет | `mobile/` - live, builder, home, history близко к web; тема через `useAppColors`; техника через API |
| E Часы + Quest native | **снят** | HealthKit/Health Connect остаются, RPG-слой (XP, кампания, hero) убран |

## Обещание

Быстрая запись подхода на телефоне (позже на часах), понятный прогресс, возврат после перерыва без наказания. Никаких XP, уровней, кампаний и ачивок: профессиональный инструмент, а не игра.

## Архитектура

```text
PWA:  routes/components → stores → domain → storage
RN:   mobile/app → mobile/src/storage → domain (shared)
```

Священный цикл:

```text
PWA: /workouts/[planId] → /live/[planId] → /workouts/summary
RN:  / → /plan/[id] → /live/[planId] → /summary/[id]
```

### Переносить

- Модель планов / сессий / подходов / рекордов (`domain/`)
- Repo-контракты, ID, input limits
- JSON backup v1 (`exportData.ts`)
- Merge / outbox / tombstones
- UX цикла: прошлый раз, rest, одна CTA
- i18n и каталог как контент

### Не переносить как есть

- Svelte UI / stores
- `localStorage` / PWA install heuristics
- HealthKit как единственное хранилище
- Одну кроссплатформенную UI-абстракцию раньше контрактов данных
- watchOS + Wear OS + Garmin одновременно в первом релизе

## Фаза D: RN ядро

| Часть | Решение |
|---|---|
| UI | Expo Router (`mobile/`) |
| Storage | AsyncStorage + те же ключи domain |
| Поведение | pure TS из `src/lib/domain` |
| Cloud | Supabase + outbox; local-first first |
| Web | миграция / SEO / техника, пока импорт не проверен |
| Часы | не в scope D |

В ядро: планы, прошлый раз, подходы, rest, autosave, resume, история, export. Без питания, readiness, маркетплейса программ, соцсети как центра.

**Подсказки веса (web + RN, domain).** `suggestedSetPerformance` кормит чип «Как в прошлый раз» на тренировке: вес и повторы берутся из того же номера подхода прошлой сессии, иначе из последнего рабочего подхода.

`nextWeightHint` (веб `LiveSetPanel`, RN `WeightCue`) считает уже не от фиксированной плиты, а от оценки 1ПМ:

- `exerciseOneRepMax` берёт лучший подход за последние 6 касаний упражнения и считает Эпли (`w × (1 + повторы / 30)`), только для 1–12 повторов: дальше это выносливость, а не сила. Подходы «в отказ» важнее обычных: это честный предел, поэтому при их наличии оценка строится по ним, а не по подходу с запасом;
- рабочий вес на целевые повторы = доля от этого максимума (для 8 повторов около 79%); целевые повторы берутся из **текущего** пресета (`exercise.targetReps`), поэтому неделя цикла с другими повторами не получает вес прошлой недели;
- `raise`: план по подходам и повторам закрыт. Вес берётся из оценки, но не меньше одного шага и не больше +10% к прошлой вершине, поэтому 12 повторов не превращаются в прыжок на 7.5 кг;
- `repeat`: план недобран или целевые повторы выросли - вес держится, добавка только сорвала бы новые повторы;
- `ease`: два промаха подряд - минус один шаг, а не вечное «повтори»;
- `failure-hold`: план закрыт, но верхний подход был «в отказ» - нагрузка уже на пределе, вес держится;
- `failure-ease`: отказ случился раньше запланированных подходов/повторов - минус один шаг;
- `wave`: каждое 4-е касание - примерно 90% от прескрипции;
- снаряд задаёт `LoadProfile` (`loadProfileForEquipment`): шаг 2.5 кг и пустая штанга 20 кг, EZ/SZ-гриф 10 кг, гантели 2 кг, гири 4 кг. `snapLoad` не опускает вес ниже пустого снаряда и всегда попадает на реально набираемую комбинацию: «12.5 кг на 20-килограммовой штанге» - не вес.

Панель показывает `1ПМ ≈ N кг`, `% от 1ПМ` и «включая гриф N кг» у штанги; тексты `quest.nextHint`, `quest.nextHintRepeat`, `quest.nextHintEase`, `quest.nextHintWave`, `quest.nextHintFailureHold`, `quest.nextHintFailureEase`, `quest.estimatedMax`, `quest.ofMax`, `quest.barIncluded`. Цикл больше не ограничивается подходами и повторами: `cycleTargets.ts` добавляет к ним вес по той же модели (`cycleWeekTargets` -> `live.startFromPlan({ weights })`), а сохранённый план не перезаписывается.

## Фаза F: тренер ↔ клиент (Фаза 2 плана)

**Статус (v0.24.0):** связь, кабинет тренера (web + RN), просмотр подходов, отзыв клиентом, **назначение плана** (`coach_assignments`) - в продукте. Клиент видит назначение на Главной и в профиле, импортирует снимок одним нажатием; план закрепляется следующим. Кабинет: компактный инвайт, поиск клиентов, строка «последняя тренировка», на десктопе две колонки. Профиль: блок «Тренер и клиенты» из двух строк, код и отключение — в шторке. ИИ-тренер: баланс за 30 дней, подсказки по выпавшим группам, добавление в выбранный план, скрытие на 7 дней, точка в профиле. В Справочнике — статьи про режим тренера и ИИ-тренера со скриншотами. Новый полупрозрачный вид панелей и шапок; экраны загрузки приведены к нему.

**Работа:** тренер готовит следующую тренировку → клиент пишет подходы обычным циклом → тренер открывает готовую сессию. Кабинет кормит священный цикл клиента, не заменяет его.

```text
Код в профиле → Назначить план → Клиент: старт и подходы → Тренер: сессия по упражнениям → снова назначить
```

**Связь (готово):**

- `CoachClientLink`: `pending → active → revoked`, отзыв необратим, лимит 50 активных.
- Инвайт-код: 8 символов, алфавит без I/L/O/U, нормализация OCR, формат `ABCD-1234`.
- Имя клиента в `note` при accept (`coach_display_name`).
- SQL: `~/.repdraft-sql/coach-mode.sql` (+ патчи session detail / client revoke).
- Клиент: `storage/coachRepository.ts`, web `/clients`, приём кода в профиле; RN: кабинет отдельно от экрана подсказок `/coach`.

**Карточка клиента (не CRM):** имя + одна строка статуса (тир по дням без тренировки) + строка «Последняя: {план} · {когда}». Тап раскрывает список последних сессий, тап по сессии - подходы. Сетка «7 дней / подходы / тоннаж» на карточке не нужна (подходы и тоннаж в stats - за всё время; путаница с подписью «7 дней»). Сводка «занимались за 7 дней» - над списком, поиск - при 5+ клиентах. Блок инвайта - компактная карточка: слева на десктопе (от 1280px), сверху в стеке на телефоне; сворачивать при наличии клиентов не нужно.

**Просмотр сессии:** security definer RPC по id при `status = active`. Тренер не читает `workout_sessions` напрямую. Упражнения и подходы в ответе; имена - из каталога на клиенте.

**Клиент в профиле:** кто тренер, «Отключиться» (RPC: RLS не даёт клиенту отозвать `active`), код приглашения.

**Назначение плана (готово, SQL вне git — `~/.repdraft-sql/coach-plan-assignment.sql`):**

1. `coach_assignments`: снимок плана (`plan_name` + `plan_exercises`) на момент выдачи, не живая ссылка. Одно `current` на клиента (партиальный уникальный индекс), новое вытесняет старое в `superseded`.
2. RPC: `coach_list_assignable_plans`, `coach_assign_plan`, `coach_my_current_assignment`, `coach_discard_my_assignment`. Коды `RDC06` план не найден, `RDC07` нет активной связи, `RDC08` пустой план.
3. Клиент импортирует снимок как свой план (`plans.importPlan` / RN `importAssignedPlan`) и пин «следующая» (`homeNextPlan`). План становится обычным локальным планом.
4. UI: «Назначить тренировку» в раскрытой карточке клиента → пикер своих планов; у клиента карточка «Тренер назначил план» в профиле с «Добавить» / «Отклонить».

Осталось: «план vs факт» уже в итоговой тренировке web + RN (`planVsActualParts`, строка под названием упражнения, план приглушается при недоборе). Тренер пока видит сырые подходы клиента, отдельного сравнения с целями плана на его стороне нет.

**Вне scope:** чат, питание, маркетплейс программ, биллинг клиентов тренера, оплата тренера (Stripe / ЮKassa) до тех пор, пока петля не используется.

## Часы (фаза C/E, кратко)

Один стек после ясности аудитории. Минимум: сегодня → упражнение → confirm set → rest → finish → короткий итог. Session ownership телефон vs часы. Offline / kill / разрядка не теряют сессию.

## Контракты между клиентами

1. Типы и merge rules в `domain`
2. `EXPORT_VERSION` / backup shape
3. Local-first, затем cloud; outbox kinds
4. Устойчивые ID (`isCloudPersistableId`)
5. Tombstones / delete reconcile
6. Master активной сессии (телефон vs часы)
7. Идемпотентность импорта и sync

## Миграция

```text
Backup → import in native → сверка → confirm → sync
```

PWA export не убирать, пока перенос не проверен на реальных тренировках.

## Вне scope без явного запроса

Четыре клиента сразу, Garmin-как-обещание, платные XP / loot / daily streaks, B2B тренер, AI-коуч как центр, RPG для сна/питания.

## Правило решений

Священный цикл не должен стать медленнее. Новые фичи не оправдываются «потому что rewrite».

## Публичные программы и рейтинг сессии

`/programs` - контент, а не новый движок: шаблон (недели × сессии + фокус по группам) лежит в `src/lib/domain/programs.ts`, план собирается `buildSessionExercises` из локального каталога и сохраняется через `plans.importPlan`. Ничего не скачивается, повторный вход даёт тот же план (детерминированный выбор по популярности).

Прогресс программ - локальный (`repdraft:program-runs`): слот хранит `planId`, а выполнение подтверждается только завершённой сессией с этим `planId` (`reconcileWithFinishedPlans`). Это единственный честный сигнал, доступный без БД.

Рейтинг сессии 1–5 - локальный (`repdraft:session-ratings`) на web и RN, одна панель на итогах. В `workout_sessions` колонки нет; ключ хранения отдельный, чтобы будущая миграция в БД прошла без переписывания sync.

Оценка не должна быть записью в никуда: `ratingFor` читается в строке истории (чип «★ 4» через `translatePlural`-мету) и в деталях завершённой тренировки (та же панель с `variant="detail"`, заголовок «Ваша оценка», можно переставить). Стор гидратируется один раз в `+layout.svelte`; в RN то же делает `sessionRatingsRepo.all()` при `useFocusEffect` в истории. Когда появится колонка в БД, чип и панель продолжат работать без правок UI.

Web-only остаётся UI библиотеки программ; RN-паритет - следующий шаг, когда появится смысл тащить генератор планов в приложение.
