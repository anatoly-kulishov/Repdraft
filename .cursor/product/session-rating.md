# Session rating (1-5): что делает сейчас и идея для ИИ

Статус: реализовано только «сохранить и показать». Использование в расчётах - идея
из бэклога (2026-11-22), кода нет.

## Что есть сейчас

| Что | Где |
|---|---|
| Карточка со звёздами после финиша | `src/lib/components/summary/SessionRatingPanel.svelte` на `/workouts/summary` |
| Та же карточка в деталях сессии | `/workouts/history/[id]` (вариант `detail`) |
| Чип с оценкой в списке истории | `src/routes/workouts/+page.svelte` (`.entity-row__rating`) |
| Хранение | `repdraft:session-ratings` -> `{ [sessionId]: { stars, at } }`, только устройство |
| Web-стор | `src/lib/stores/sessionRatings.ts` (гидратация в `+layout.svelte`) |
| RN-стор | `mobile/src/storage/sessionRatingsRepo.ts` |
| Домен + self-check | `src/lib/domain/sessionRating.ts` (`runSessionRatingSelfCheck`) |

Ключевые свойства:

- **Локально и осознанно.** У `workout_sessions` нет колонки rating, синка нет:
  смена устройства или переустановка стирают оценки. Причина описана в шапке
  `sessionRating.ts` (тихий дроп в облаке выглядел бы как потеря данных).
- **Ни на что не влияет.** Оценку не читают ни `generatePlan` / `tunePlan` /
  `tunePrescription`, ни недельная нагрузка, ни графики прогресса, ни коуч-режим.
  Это личная заметка «как прошло» на будущее.
- **Копирайт обещает локальность**: `rating.hint` = «Оценка хранится на устройстве
  и не отправляется в облако». В `/privacy` оценки прямо не названы: в списке
  локальных данных (`privacy.s2Body`) их нет, добавить при реализации.

## Идея: оценка как сигнал самочувствия для ИИ

Зачем: все запросы к модели сейчас бесконтекстные. В `tunePlan` уже есть правило
«полегче / мало сил / после болезни -> минус подход», но модель не знает, что
атлету реально тяжело: в теле запроса только план и свободный бриф. Оценка - единственный
субъективный сигнал в приложении, и он бесплатно лежит в localStorage.

Порог входа: минимум 2 оценки из последних 5 сессий, иначе сигнала нет (оценки
ставят не на каждую тренировку).

### Вариант A: вклеить в бриф (дешево, без сервера)

Паттерн уже есть: `appendAthleteProfileToBrief()` (`src/lib/domain/athleteProfile.ts`)
дописывает профиль атлета в текст брифа на клиенте, сервер про это не знает.

1. `recentReadiness(ratings, n = 3)` в `sessionRating.ts`: сортировка по `at`,
   берём последние `n`, считаем `stars[]`, `avg`, `lowStreak` (сколько низких
   (<= 2) подряд с конца).
2. Хелпер рядом с `appendAthleteProfileToBrief`: `appendReadinessToBrief(brief, readiness, locale)`.
   Строка вида `самочувствие: 2, 2, 3 из 5, две подряд тяжёлые`.
3. Вклейка в трёх местах: `PlanTuneSheet.svelte`, `BuilderAiTuneSheet.svelte`,
   `/ai` (`src/routes/ai/+page.svelte`, там же где профиль).
4. В `replyKey` кэша `tune-plan/+server.ts` добавить строку про самочувствие:
   иначе повтор с другой оценкой получит закэшированный ответ под старое состояние.

Плюсы: 2-3 файла, ноль изменений API и схемы. Минусы: свободный текст, модель может
проигнорировать, клэмпа нет.

### Вариант B: структурное поле + детерминированный клэмп (контроль)

1. Тело `/api/ai/tune-plan` (и `/api/ai/tune`): `readiness: { avg, stars, lowStreak, n }`.
   Валидация только числами: `avg` 1-5, `n <= 5`, `stars` - короткий массив 1-5.
   Никакого свободного текста от клиента в этом поле.
2. Вставка блока в `{extra}` шаблона `SYSTEM_TEMPLATE` в `tunePlan.ts`.
3. Клэмп после `normalizePlanTuneRows`, чтобы модель не могла «нафантазировать»
   восстановление:

| Сигнал | Принудительно |
|---|---|
| `avg <= 2` или 2 низкие подряд | `sets = min(sets, 3)`, максимум 7 упражнений, `restSec` не режем |
| `avg >= 4.5`, 3 высокие подряд | `+1` подход, но не выше `MAX_SETS` (6) |
| `n < 2` | поле не отправляем, поведение как сейчас |

4. Пороги держать в одном месте (`READINESS_LOW_MAX`, `READINESS_HIGH_MIN`,
   `READINESS_MIN_SAMPLES`), а не размазывать по промпту и коду.

## Что обязательно поменять вместе с этим

1. **Приватность.** `rating.hint` обещает «не отправляется в облако»; в
   `privacy.s2Body` оценки даже не перечислены среди локальных данных. При
   реализации: добавить оценки в список локального хранения и переписать подсказку
   («хранится на устройстве; усреднённая оценка уходит в ИИ при запросе плана»).
   Без правки текстов это ложь в UI.
2. **Разреженность.** Оценки есть не у всех и не всегда; без порога «2 из 5»
   модель будет строить выводы по одной случайной двойке.
3. **Streak, а не средняя.** Одна двойка = плохой день. Реагируем на 2-3 низкие подряд.
4. **`at` - время оценки, не тренировки.** Обычно сразу после финиша, но оценка
   из истории через неделю сдвинет порядок. Строгий вариант: джойн с датой сессии
   из локальной истории.
5. **Обратная связь в UI.** Подстройка иначе невидима: показать в `summary` ответа
   строку «учёл, что две тренировки подряд на 2 из 5» (поле уже есть).
6. **RN-паритет.** Строка `rating.hint` общая (`tt('rating.hint')`), стор на RN есть.
   Но шит подстройки плана на RN ещё не построен (`.cursor/product/plan-tune.md`),
   поэтому вариант A на RN подключается только вместе с ним.
7. **Квота.** Не плодить лишние вызовы: сигнал едет внутри существующего запроса,
   а не отдельным «оцени состояние».

## Проверки

- `runSessionRatingSelfCheck`: `recentReadiness` (порог, порядок по `at`, streak, пустой стор).
- Юнит на клэмп: `avg 2` -> `sets <= 3`; `avg 5` -> не больше `MAX_SETS`.
- `replyKey` включает readiness: одинаковый план + разная оценка = разные ключи.
- E2E: `page.route('**/api/ai/tune-plan')` и проверка тела запроса (как в manual QA
  из `plan-tune.md`), без живого провайдера.

## Порядок работ, если решим делать

1. `recentReadiness` + self-check (чистый домен, тестируется без UI).
2. Вариант A: бриф в `/ai` (самый простой вход, видно по summary ответа).
3. Вариант B: поле + клэмп в `tune-plan` (там же ключ кэша).
4. Копирайт: `rating.hint`, `/privacy`, запись в changelog.
